= Event Filtering

`EventFilter` selects what `SessionService.getEvents(id, filter)` returns.
It decides four things:

* whether the read covers the whole log or only the active view;
* which event types and message types are included;
* whether the synthetic summary events are included;
* how many events, through a window.

It is a read-side filter.
An event the filter excludes stays in the log and is only left out of the result.

== Shortcuts

[source,java]
----
// Every event of the log, boundaries and covered events included
sessionService.getEvents(id, EventFilter.all());

// The message events of the active view: the context window
sessionService.getEvents(id, EventFilter.active());

// The newest 20 events, extended to the start of the turn the window lands in
sessionService.getEvents(id, EventFilter.lastN(20));
----

== Builder

[source,java]
----
EventFilter filter = EventFilter.builder()
    .activeView(true)                                         // the view instead of the log
    .messageTypes(Set.of(MessageType.USER, MessageType.ASSISTANT))
    .eventTypes(Set.of(EventType.MESSAGE))                   // any type, your own included
    .excludeSynthetic(true)                                   // no summary events
    .lastN(50)                                                // window: the newest 50 matches, whole turns
    .build();

EventFilter again = filter.toBuilder().lastN(10).build();
----

[cols="1,1,3"]
|===
| Field | Type | Description

| `activeView`
| `boolean`
| Applies the filter to the active view instead of the whole log when `true`.
The view is what the newest compaction boundary defines: the pinned events, the summary and the preserved events first, then everything appended since.
`EventFilter.active()` sets it.

| `messageTypes`
| `Set<MessageType>`
| Keeps only the events that carry a message of these types.
An empty set means no restriction.

| `eventTypes`
| `Set<EventType>`
| Keeps only the events of these types.
This is how the runtime state is read: `STATUS`, `INTERRUPT`, `QUESTION` and `ANSWER` for the xref:api/session/turn-status.adoc[turn status], and an application's own types such as `EventType.of("MY_APP.PROGRESS")`.
An empty set means every type.
`EventFilter.active()` sets `MESSAGE`.

| `excludeSynthetic`
| `boolean`
| Leaves out the synthetic events a compaction wrote when `true`.

| `window`
| `EventFilter.Window`
| Limits the result to the newest events.
`Window.ALL` is the default; `Window.last(n)` is what the builder's `lastN(n)` sets, and `n` must be positive.
|===

The order of evaluation matters.
The view is applied first, then the criteria, and the window last, to the events that matched.

== Windows keep turns whole

A `lastN` window is a lower bound, not an exact count.
When its oldest event is not a xref:api/session/concepts.adoc#session-concepts-turn[turn start], the window is extended back to the nearest turn start before it.
This is what keeps a result from beginning with an assistant reply whose question was cut off, a tool result without its tool call, or a summary without its shadow prompt.
A tool call is therefore never returned without its results, and a prompt built from the window is one every provider accepts.

----
log:          U1 A1 U2 A2[tool call] T2[result] A2'
lastN(2):     U2 A2[tool call] T2[result] A2'      extended from "T2 A2'" to the turn start
lastN(5):     U1 A1 U2 A2[tool call] T2[result] A2'
----

The extension is bounded by one turn, and it is skipped when it cannot apply:

* a window that lands in a preamble of events before the first turn returns the plain window;
* a `messageTypes` filter that hides the user messages returns the plain window too.

A window larger than the log returns the log.

`EventFilter.apply(events)` is the reference implementation of the whole read, for a log held as a list.
The JDBC repository pushes the criteria and the window down to SQL, and extends the window with one bounded extra query when it lands mid-turn.

== Merging filters

`EventFilter.merge(other)` combines two filters into one.
The other filter's types and window replace this filter's, with one exception: a `Window.ALL` on the other side leaves the window alone.
The two flags are OR-ed, so either side can opt in.
`SessionMemoryAdvisor` merges a xref:api/session/chat-client.adoc#session-chat-client-filter[per-request filter] over its own this way.
It always merges in `EventFilter.active()` as well, so the prompt never sees the events a compaction covered.

[source,java]
----
EventFilter merged = EventFilter.lastN(50).merge(EventFilter.lastN(5));
// merged.window() == Window.last(5): the request-level window wins

EventFilter view = EventFilter.lastN(50).merge(EventFilter.active());
// the window stays, the view flag and the MESSAGE type come in
----

== What is stored

`EventFilter` decides what a read returns.
What is stored in the first place is decided on the write side.
`MessageFilter` on the `SessionMemoryAdvisor` says which messages are persisted at all; see xref:api/session/chat-client.adoc#session-chat-client-stored[What is stored].
