[[session-concepts]]
= Session Concepts

Session memory is built on five closely related concepts.
A *session* identifies one conversation.
Its *events* are the log of what happened in it.
The events group into *turns*, one per user message.
The *status* says whether a turn is running right now, and why the last one ended.
And the *active view* is the part of the log the model gets to see.
This page takes them one at a time, and ends with the `SessionService` API that ties them together.

image::session/session-core-classes.svg[The core session types, width=800, align="center"]

[[session-concepts-session]]
== Session

A `Session` is the identity of one continuous conversation.
It is an immutable value that holds only metadata.
The events are not part of it: they are stored separately and read on demand, so a `Session` stays cheap to pass around no matter how long the conversation gets.

[cols="1,3"]
|===
| Field | Description

| `id`
| The session's identifier.
It comes from the create request, or it is a random UUID.

| `createdAt`
| When the session was created.

| `expiresAt`
| When the session expires.
A session the service creates always has one: the request's `timeToLive`, or the service's default of 60 days.
A `Session` built directly with its builder has none, and never expires, unless the builder sets one.

| `metadata`
| Arbitrary metadata: the owner, the agent attributes, tags, and whatever else the application wants to keep with the session.
|===

Note that a session has no owner field.
Who it belongs to is just an attribute of its metadata, stored the way Spring Session stores its principal-name index.
Every store indexes `SessionAttributes.PRINCIPAL_NAME`, so `findByMetadata(SessionAttributes.PRINCIPAL_NAME, "alice")` lists the sessions of a user.
The same goes for the agent a session runs: `SessionAttributes.AGENT_NAME`, `AGENT_VERSION` and `AGENT_MODEL` label it, for listings and a UI, and `SessionAttributes.agentName(session)` reads the name back.

[source,java]
----
Session session = sessionService.create(CreateSessionRequest.builder()
    .id("session-abc")                       // optional: a random UUID otherwise
    .timeToLive(Duration.ofDays(7))          // optional: the service's default otherwise
    .metadata(SessionAttributes.PRINCIPAL_NAME, "alice")
    .metadata(SessionAttributes.AGENT_NAME, "support")
    .build());
----

Creating a session whose id is already taken throws `SessionAlreadyExistsException` and leaves the existing session untouched.
This is what makes concurrent first use safe: when two callers create the same id at the same time, one of them gets the session and the other gets the exception, and the second can simply read what the first created.

[[session-concepts-event]]
== SessionEvent

A `SessionEvent` is an immutable value with an `EventType`.
Most events are `MESSAGE` events.
A `MESSAGE` event wraps a Spring AI `Message` and adds only what the message intentionally leaves out: an identity, the session it belongs to, its position in the log, and a few framework flags.
Every other event type records runtime state in the same log, a compaction boundary or a turn transition for example, and carries its data in a `payload` map instead of a message.

[cols="1,3"]
|===
| Field | Description

| `id`
| The event's identity, a random UUID by default.
Event ids are unique across sessions, not only within one.

| `sessionId`
| The session the event belongs to.

| `timestamp`
| When the event was recorded, `Instant.now()` by default.

| `type`
| What the event records.
`MESSAGE`, the default, is a conversation message.

| `message`
| The Spring AI message of a `MESSAGE` event.
`getMessage()` throws for an event that has none, so test with `hasMessage()` first.

| `payload`
| The JSON-serializable data of an event that is not a message.
Empty for a message event.

| `metadata`
| Framework flags such as `METADATA_SYNTHETIC`, `METADATA_COMPACTION_SOURCE` and `METADATA_COMPACTION_ID`, plus whatever the application adds.
|===

An event is appended once and never changed afterwards.
Compaction does not flag it or move it either.
It appends a `COMPACTION` event that defines the view from then on, as <<session-concepts-view>> explains.

[source,java]
----
// A message event, timestamped now
SessionEvent event = SessionEvent.builder()
    .sessionId(sessionId)
    .message(new UserMessage("Hello"))
    .build();

// With metadata and a deterministic timestamp (useful for tests)
SessionEvent custom = SessionEvent.builder()
    .sessionId(sessionId)
    .timestamp(Instant.parse("2026-06-01T12:00:00Z"))
    .message(new AssistantMessage("Response"))
    .metadata("model", "gpt-5")
    .build();

// An event of the application's own: no message, a payload instead
SessionEvent progress = SessionEvent.builder()
    .sessionId(sessionId)
    .type(EventType.of("MY_APP.PROGRESS"))
    .payload("step", "research")
    .build();
----

=== Event types

`EventType` is open: a type is nothing more than its name, and an application can define its own.
Six types are well known:

* `MESSAGE`, a conversation message.
* `COMPACTION`, a compaction boundary.
Its payload is a `CompactionBoundary`.
* `STATUS`, a transition of the <<session-concepts-status,turn status>>.
* `INTERRUPT`, a request to stop the turn that runs.
* `QUESTION`, what a parked turn waits on.
Its payload is a `Question`.
* `ANSWER`, the answer a turn resumed with, pointing at its question by event id.
Its payload is an `Answer`.

Your own types are created with `EventType.of("MY_APP.PROGRESS")`.
A name is upper case letters, digits, underscores and dots, at most 64 characters long.
Every store keeps the name as it is, and a filter by type works for any of them.
Only `MESSAGE` events take part in prompt assembly and compaction, though: the other types are runtime state, not conversation.

`EventType.canCarryMessage()` says whether an event of the type holds a message.
`SessionService.getMessages()` and `getActiveMessages()` skip the events that do not.

=== Message types

[cols="2,1,3,3"]
|===
| Message | Synthetic | Meaning | Compaction

| `UserMessage`
| no
| Real user input; it starts a turn
| Covered with its turn

| `AssistantMessage`
| no
| The agent's reply, with or without tool calls
| Covered with its turn, never separated from its tool results

| `ToolResponseMessage`
| no
| A tool's output
| Covered with its turn

| `SystemMessage`
| no
| A stored system prompt: configuration, not conversation; storing one is opt-in
| The latest one is pinned first in the view, earlier ones are covered; never summarized.
See xref:api/session/system-messages.adoc[System Messages]

| `UserMessage`
| yes
| The shadow prompt that opens a summary turn
| Pinned by a plain window; replaced and covered by the next summary

| `AssistantMessage`
| yes
| The summary that closes a summary turn
| As above; its text is fed to the next summary as the prior summary
|===

The synthetic events are the ones a compaction wrote.
`SessionEvent.isSynthetic()` is `true` for them, and `EventFilter.excludeSynthetic(true)` hides them from a read.

[[session-concepts-turn]]
== Turn

A turn is the atomic unit of a conversation: one user message plus everything that follows it up to the next user message.
That is the assistant replies, the tool calls and the tool results.
It is the same unit xref:api/chat-memory.adoc[chat memory] evicts by, and it is what one `ChatClient` call with all of its tool rounds amounts to.
One model call within a turn is a round.

----
Turn 1: [USER "What is Spring AI?"]  [ASSISTANT "Spring AI is..."]
Turn 2: [USER "Can it use tools?"]   [ASSISTANT (tool call)]  [TOOL result]  [ASSISTANT "Yes, ..."]
Turn 3: [USER "Show me an example"]  [ASSISTANT "Here is..."]
----

Working with turns rather than message counts is what keeps a compaction from splitting a tool call from its result, or from covering a reply while keeping the question that prompted it.
Reads follow the same rule.
A `lastN` window is extended back to the start of the turn it lands in, using the user messages `SessionEvent.isTurnStart()` marks, so a prompt built from a window never begins in the middle of a turn either.
Turns are also what a `TurnCountTrigger` counts: `CompactionRequest.currentTurnCount()` counts the non-synthetic user messages, so the shadow prompt of a summary turn does not inflate the count.
When a harness runs a turn through the session's status, the turn runs under the harness's run id; see <<session-concepts-status>>.

[[session-concepts-status]]
== Status

Besides its messages, a session carries the status of its turns: whether a turn runs right now, under which run, why the last one ended, and what it waits on when it stopped to ask.
Like the active view, the status is a projection of the log, not a column: `STATUS`, `INTERRUPT`, `QUESTION` and `ANSWER` events record the transitions, and the status is the newest `STATUS` event, or `IDLE` when there is none.
Every harness reads and sets it through `TurnService`, which `sessionService.turns()` returns.
So a turn started on one instance can be interrupted from another, a UI can show that an agent is busy or waits for a decision, and two harnesses never run one session at once.
xref:api/session/turn-status.adoc[Turn Status] has the methods, the lease that frees a session after a crash, and how a turn parks on a question and resumes with the answer.

[[session-concepts-view]]
== The active view

The log is append-only.
An event is appended once and is never edited, moved or flagged afterwards.
What changes over time is the *view*: the part of the log that is sent to the model.

A compaction appends a `COMPACTION` boundary event that names, by id, the events the view starts with:

* the pinned events, that is the latest stored system message and, for a plain window, the earlier summary;
* the summary events that stand in for what was covered;
* the preserved recent events.

Everything appended after the boundary is in the view as well.
Everything else before the boundary is *covered*.

image::session/session-event-lifecycle.svg[The lifecycle of an event, width=500, align="center"]

So an event is in one of three states:

* *In the view:* part of the context window.
* *Covered:* the newest boundary does not name it.
It is an old turn, a stored system message a newer one superseded, or a summary a newer summary replaced.
A later boundary only ever names events from the view it compacted, so a covered event stays covered.
It is still in the log, and `EventFilter.all()` still reads it.
* *Gone:* only when the whole session is deleted, with `delete` or `deleteExpiredSessions`.
Compaction never deletes anything.

The view is a projection.
A read with `EventFilter.active()` returns the events the newest boundary names, in the boundary's order, followed by everything appended since.
`CompactionBoundary.project(log)` is the reference implementation.
Keep in mind that the view is the conversation: a boundary names message events, so an event of another type logged before the boundary is not in the view, while one logged after it is.
Read runtime state from the log directly, with `eventTypes` and without the view.

[[session-concepts-service]]
== SessionService

`SessionService` is the API an application and the advisors use.
`DefaultSessionService` implements it on top of a `SessionRepository`.
The diagram shows a session from creation to cleanup; any integration drives it the same way, your own loop as well as the `ChatClient` advisors.

image::session/session-lifecycle-sequence.svg[A session from creation to cleanup, width=800, align="center"]

[source,java]
----
SessionService sessionService = DefaultSessionService.builder()
    .sessionRepository(InMemorySessionRepository.builder().build())
    .defaultTimeToLive(Duration.ofDays(30))    // 60 days by default
    .allowSystemMessages(false)                // the default; see System Messages
    .build();

// 1. Create
Session session = sessionService.create(CreateSessionRequest.builder().build());

// 2. Run a turn: start it, append its events (the shorthand wraps a Message in a
//    SessionEvent), end it
TurnStatus turn = sessionService.turns().start(session.id(), null);
sessionService.appendMessage(session.id(), new UserMessage("What is Spring AI?"));
sessionService.appendMessage(session.id(), new AssistantMessage("Spring AI is..."));
sessionService.turns().end(session.id(), turn.runId(), StopReason.END_TURN);

// 3. The active view, as messages for a prompt
List<Message> history = sessionService.getActiveMessages(session.id());

// 4. The whole log, as events
List<SessionEvent> log = sessionService.getEvents(session.id(), EventFilter.all());

// 5. Compact when a trigger fires
sessionService.compact(session.id(), new TurnCountTrigger(20),
        WindowCompactionStrategy.builder().lastTurns(10).build());

// 6. Delete one session, or every expired one from a scheduler
sessionService.delete(session.id());
int removed = sessionService.deleteExpiredSessions(Instant.now());
----

[cols="1,3"]
|===
| Method | Description

| `create(CreateSessionRequest)`
| Creates a session with the request's id, time to live and metadata.
Throws `SessionAlreadyExistsException` when the id is taken.

| `findOrCreate(CreateSessionRequest)`
| Returns the session with the request's id, and creates it from the request when there is none.
Safe under concurrent first use: the stored session wins.

| `findById(id)`
| Returns the session, or `null`.

| `findByMetadata(name, value)`
| Returns the sessions whose metadata holds the value under an indexed key, oldest first.

| `appendEvent(event)`, `appendMessage(id, message)`
| Appends an event to the log.
A `SystemMessage` is rejected unless `allowSystemMessages(true)` is set.

| `appendEvents(id, events, expectedVersion)`, `getEventVersion(id)`
| The version-checked append and the version it checks.
Several events are written atomically, and only if the log is still at the version that was read.
This is how the compaction and the turn status are recorded; see <<session-concepts-concurrency>>.

| `getEvents(id, filter)`, `getEvents(id)`
| Returns the events a xref:api/session/event-filter.adoc[filter] selects, in log order, or the whole log without one.

| `getMessages(id)`, `getActiveMessages(id)`
| Returns the messages of the whole log, or of the active view.

| `turns()`
| Returns the `TurnService`: `status`, `start`, `end`, `interrupt`, `park`, `pendingQuestion` and `resume`, all on this service; see <<session-concepts-status>>.

| `compact(id, trigger, strategy)`
| Evaluates the trigger on the active view and, when it fires, runs the strategy and records the result.
See xref:api/session/compaction.adoc[Compaction].

| `delete(id)`
| Deletes the session and its events.
There is no tombstone.

| `deleteExpiredSessions(before)`
| Deletes every session that expired before the instant, with its events, and returns the count.
Sessions are not swept automatically: call it from a scheduler.
|===

=== Idempotent appends

A retried `appendEvent` for an id that was already committed is a no-op.
It is neither an error nor a duplicate, and it does not advance the log's version.
`InMemorySessionRepository` checks the session's events for the id; `JdbcSessionRepository` looks it up before inserting.
In the JDBC store the event id is the primary key of the whole event table, so reusing an id that belongs to another session throws `IllegalStateException` rather than being treated as a replay.
The default id is a random UUID, so none of this matters unless a caller supplies its own ids.

[[session-concepts-concurrency]]
=== Optimistic concurrency

The log has a version.
`getEventVersion(sessionId)` is a counter that advances on every append of a new event and on every successful `appendEvents` call.
`appendEvents(sessionId, events, expectedVersion)` writes several events atomically, but only if the log is still at that version.
Both methods are on the `SessionRepository` and on the `SessionService`, so a harness can record state of its own the same way the service does.

The compaction is the main user.
`DefaultSessionService.compact` reads the version, then the newest boundary, then the view.
It builds the boundary and the summary events from the strategy's result and passes the version to `appendEvents`.
When another writer changed the log in between, the compare-and-swap returns `false`, and what happens next depends on who got there first:

* If a newer boundary landed, this result is dropped.
It stands on a view that is gone.
* If it was an append, the result is rebased.
The events appended since the view was read join the preserved tail verbatim, the same summary stands, and the write is retried, twice at most.

So an append does not waste the summary, a compaction never covers what the model was about to see, and only a session that keeps overtaking the write makes it stand down until the next pass.

The <<session-concepts-status,turn status>> is recorded the same way.
`start` reads the version and the newest status, refuses when a turn runs, and appends the `STATUS` event against the version, so two harnesses cannot both start a turn.
A write that an append overtook is re-read and retried, five times in all.
A status event that lands between a compaction's reads and its write costs the compaction one rebase with nothing to rebase, since the view is message events only.
The turn advisor ends the turn before it compacts, so on the common path the two never collide.

=== Ordering

Events are returned in insertion order, not by wall-clock timestamp.
The JDBC repository keeps a monotonic `seq` column for this.
That is why the summary events a compaction writes, stamped with the compaction time, still sit where the boundary places them.
