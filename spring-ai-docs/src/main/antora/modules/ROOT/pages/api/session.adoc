[[Session]]
= Session

A session keeps a conversation as an append-only log of events.
The prompt the model sees is built from a view of that log, not from the log itself.
xref:api/chat-memory.adoc[Chat Memory], which it succeeds, stores a flat list of messages per conversation id.
A session adds what an agent needs over a long conversation:

* *Structured events.*
Every message is a `SessionEvent` with an id, a timestamp, its session and metadata.
Other event types record what happened in the same log.
* *Turn-aware compaction.*
Triggers decide when the history grew too large.
A strategy decides what leaves the view, always on a turn boundary, so the model never sees a tool call without its result or an answer without its question.
A compaction never changes the log.
It appends a boundary that defines the view from then on.
* *A repository SPI.*
`SessionRepository` has an in-memory implementation for tests and a JDBC one for production.
A store of your own passes the same contract tests.

The session is the state.
What runs on it is not.
A `ChatClient` with the session advisors is one such runtime, a harness.
It reads the view, calls the model, appends what happened, and keeps nothing of its own.
This is what lets any instance run a turn, and another instance run the next one.
Another harness, a loop of your own for example, runs on the same session through the same `SessionService`.

The session carries the status of its turns too: which run holds the turn, and why the last one ended.
Every harness reads and sets it through the same `TurnService`, which `sessionService.turns()` returns: `status`, `start`, `end`, `interrupt`, `park` and `resume`.
So a turn started on one instance can be interrupted from another, and two harnesses never run one session at once.
A turn can also stop to ask a person something, a tool call that needs confirmation for example, and go on later with the answer.
The question and the answer are events in the log, and the session is parked in between.
See xref:api/session/turn-status.adoc[Turn Status].

[[session-modules]]
== Modules

[cols="1,1,3"]
|===
| Module | Artifact | Contents

| Session
| `spring-ai-session`
| Holds the core: `Session`, `SessionEvent`, `SessionService`, `SessionRepository` with `InMemorySessionRepository`, `EventFilter`, compaction with the `ChatModelSummarizer`, the `TurnService` with its status types, and the `Question` and `Answer` of a parked turn.
It has no dependency on `ChatClient`.

| Session Advisor
| `spring-ai-session-advisor`
| Holds the `ChatClient` integration: `SessionMemoryAdvisor`, `SessionTurnAdvisor`, `SessionInterruptAdvisor` and `SessionAdvisors`.

| JDBC Session
| `spring-ai-session-jdbc`
| Holds `JdbcSessionRepository` for PostgreSQL, MySQL, MariaDB and H2, with the schema scripts.

| Auto-configuration
| `spring-ai-autoconfigure-model-session`, `spring-ai-autoconfigure-model-session-jdbc`
| Provides the `SessionService` and `JdbcSessionRepository` beans and their properties.

| Starter
| `spring-ai-starter-model-session-jdbc`
| Brings all of the above with Spring Boot's JDBC starter.
|===

== Quick Start

Add the starter:

[source,xml]
----
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-session-jdbc</artifactId>
</dependency>
----

With a `DataSource` on the classpath, Spring Boot creates a `JdbcSessionRepository` and a `SessionService` bean.
It detects the SQL dialect from the database metadata, and it initializes the schema of an embedded database.
For PostgreSQL or MySQL in development, initialize the schema with `spring.ai.session.repository.jdbc.initialize-schema=always`.

Then wire the advisors into a `ChatClient` and pass a session id with every call:

[source,java]
----
@Bean
ChatClient chatClient(ChatModel chatModel, SessionService sessionService) {
    return ChatClient.builder(chatModel)
        .defaultAdvisors(SessionAdvisors.builder(sessionService)
            .compaction(new TurnCountTrigger(20), WindowCompactionStrategy.builder().lastTurns(10).build())
            .build())
        .build();
}

String answer = chatClient.prompt()
    .user("Hello!")
    .advisors(SessionAdvisors.session("session-abc"))
    .call()
    .content();
----

A session that does not exist yet is created on first use.
The session id is required on every call.
There is no fallback, because a shared default session would silently merge the history of different users.

Without Spring Boot, or in a test, build the service on the in-memory repository:

[source,java]
----
SessionService sessionService = DefaultSessionService.builder()
    .sessionRepository(InMemorySessionRepository.builder().build())
    .build();
----

NOTE: `InMemorySessionRepository` is for tests and demos.
Sessions are lost on restart and are not shared across instances.
