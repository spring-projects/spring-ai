[[Session]]
= Session Memory

Session memory keeps a conversation as an append-only log of events, and builds the prompt the model sees from a view of that log.
Where xref:api/chat-memory.adoc[Chat Memory] stores a flat list of messages per conversation id, a session adds what an agent needs over a long conversation:

* *Structured events.*
Every message is a `SessionEvent` with an id, a timestamp, its session and metadata; other event types record what happened in the same log.
* *Turn-aware compaction.*
Triggers decide when the history grew too large, and a strategy decides what leaves the view, always on a turn boundary, so the model never sees a tool call without its result or an answer without its question.
A compaction never changes the log: it appends a boundary that defines the view from then on.
* *A repository SPI.*
`SessionRepository` has an in-memory implementation for tests and a JDBC one for production; a store of your own passes the same contract tests.

== Modules

[cols="1,1,3"]
|===
| Module | Artifact | Contents

| Session
| `spring-ai-session`
| The core: `Session`, `SessionEvent`, `SessionService`, `SessionRepository` with `InMemorySessionRepository`, `EventFilter` and compaction, the `ChatModelSummarizer` included.
No dependency on `ChatClient`.

| Session Advisor
| `spring-ai-session-advisor`
| The `ChatClient` integration: `SessionMemoryAdvisor`, `SessionTurnAdvisor` and `SessionAdvisors`.

| JDBC Session
| `spring-ai-session-jdbc`
| `JdbcSessionRepository` for PostgreSQL, MySQL, MariaDB and H2, with the schema scripts.

| Auto-configuration
| `spring-ai-autoconfigure-model-session`, `spring-ai-autoconfigure-model-session-jdbc`
| The `SessionService` and `JdbcSessionRepository` beans and their properties.

| Starter
| `spring-ai-starter-model-session-jdbc`
| All of the above with Spring Boot's JDBC starter.
|===

== Quick Start

Add the starter:

[source,xml]
----
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-session-jdbc</artifactId>
</dependency>
----

With a `DataSource` on the classpath, Spring Boot creates a `JdbcSessionRepository` and a `SessionService` bean, detects the SQL dialect from the database metadata, and initializes the schema of an embedded database.
For PostgreSQL or MySQL in development, initialize the schema with `spring.ai.session.repository.jdbc.initialize-schema=always`.

Wire the advisors into a `ChatClient` and pass a session id with every call:

[source,java]
----
@Bean
ChatClient chatClient(ChatModel chatModel, SessionService sessionService) {
    return ChatClient.builder(chatModel)
        .defaultAdvisors(SessionAdvisors.builder(sessionService)
            .compaction(new TurnCountTrigger(20), WindowCompactionStrategy.builder().lastTurns(10).build())
            .build())
        .build();
}

String answer = chatClient.prompt()
    .user("Hello!")
    .advisors(SessionAdvisors.session("session-abc"))
    .call()
    .content();
----

A session that does not exist yet is created on first use.
The session id is required on every call: there is no fallback, because a shared default session would silently merge the history of different users.

Without Spring Boot, or in a test, build the service on the in-memory repository:

[source,java]
----
SessionService sessionService = DefaultSessionService.builder()
    .sessionRepository(InMemorySessionRepository.builder().build())
    .build();
----

NOTE: `InMemorySessionRepository` is for tests and demos: sessions are lost on restart and not shared across instances.
