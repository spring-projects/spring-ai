[[Session]]
= Session Memory

Session memory keeps a conversation as an append-only log of events, and builds the prompt the model sees from a view of that log.
Where xref:api/chat-memory.adoc[Chat Memory] stores a flat list of messages per conversation id, a session adds what an agent needs over a long conversation:

* *Structured events.*
Every message is a `SessionEvent` with an id, a timestamp, its session and metadata; other event types record what happened in the same log.
* *Turn-aware compaction.*
Triggers decide when the history grew too large, and a strategy decides what leaves the view, always on a turn boundary, so the model never sees a tool call without its result or an answer without its question.
A compaction never changes the log: it appends a boundary that defines the view from then on.
* *A repository SPI.*
`SessionRepository` has an in-memory implementation for tests and a JDBC one for production; a store of your own passes the same contract tests.

The modules are `spring-ai-session` (the core, with no dependency on `ChatClient`), `spring-ai-session-jdbc` (the JDBC repository), `spring-ai-session-advisor` (the `ChatClient` advisors and the model-backed summarizer), and the `spring-ai-starter-model-session-jdbc` starter, which brings them all with the auto-configuration.

== Quick Start

Add the starter:

[source,xml]
----
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-session-jdbc</artifactId>
</dependency>
----

With a `DataSource` on the classpath, Spring Boot creates a `JdbcSessionRepository` and a `SessionService` bean, detects the SQL dialect from the database metadata, and initializes the schema of an embedded database.
For PostgreSQL or MySQL in development, initialize the schema with `spring.ai.session.repository.jdbc.initialize-schema=always`.

Wire the advisors into a `ChatClient` and pass a session id with every call:

[source,java]
----
@Bean
ChatClient chatClient(ChatModel chatModel, SessionService sessionService) {
    return ChatClient.builder(chatModel)
        .defaultAdvisors(SessionAdvisors.builder(sessionService)
            .compaction(new TurnCountTrigger(20), WindowCompactionStrategy.builder().lastTurns(10).build())
            .build())
        .build();
}

String answer = chatClient.prompt()
    .user("Hello!")
    .advisors(SessionAdvisors.session("session-abc"))
    .call()
    .content();
----

A session that does not exist yet is created on first use.
The session id is required on every call: there is no fallback, because a shared default session would silently merge the history of different users.

== Concepts

=== Session

A `Session` is the identity of one continuous conversation: an `id`, a `createdAt` instant, an `expiresAt` instant (the request's time to live, or the service's default of 60 days) and a `metadata` map.
It is an immutable value; the events are stored separately and read on demand.

A session has no owner field.
Who it belongs to is an attribute of its metadata, such as `SessionAttributes.PRINCIPAL_NAME`, which every store indexes so that `findByIndex(SessionAttributes.PRINCIPAL_NAME, "alice")` lists a user's sessions.
`SessionAttributes.AGENT_NAME`, `AGENT_VERSION` and `AGENT_MODEL` label the agent a session runs, for listings and a UI.

=== SessionEvent

A `SessionEvent` is an immutable value with an `EventType`.
A `MESSAGE` event wraps a Spring AI `Message` and adds what the message does not have: an `id` (a random UUID by default), a `timestamp`, the `sessionId` and a `metadata` map.
Every other event type records runtime state in the same log and carries its data in a `payload` map instead of a message; `getMessage()` throws for such an event, so test with `hasMessage()` first.

`EventType` is open: a type is its name.
`MESSAGE` and `COMPACTION` (a compaction boundary) are the well-known ones, and an application defines its own with `EventType.of("MY_APP.PROGRESS")` (upper case, digits, underscores and dots).
Every store keeps the name and a filter by type works for any of them; only `MESSAGE` events take part in prompt assembly and compaction.

[source,java]
----
// A message event, timestamped now
SessionEvent event = SessionEvent.builder()
    .sessionId(sessionId)
    .message(new UserMessage("Hello"))
    .build();

// An event of the application's own: no message, a payload instead
SessionEvent progress = SessionEvent.builder()
    .sessionId(sessionId)
    .type(EventType.of("MY_APP.PROGRESS"))
    .payload("step", "research")
    .build();
----

=== Turn

A turn is the atomic unit of a conversation: one user message plus everything up to the next user message, that is, the assistant replies, the tool calls and the tool results.
Compaction never splits a turn, and a `lastN` read window is extended back to the start of the turn it lands in, so a prompt built from the session never begins mid-turn.

=== The active view

The log is append-only.
A compaction appends a `COMPACTION` boundary event whose payload names, by id, the events that make up the view from then on: the pinned events (the latest stored system message and, for a plain window, the earlier summary), the summary events that stand in for what was covered, and the preserved recent events.
Everything appended after the boundary is in the view too.
`EventFilter.active()` reads the view; `EventFilter.all()` reads the whole log, the covered events and the boundaries included.
`CompactionBoundary.project(log)` is the reference projection every store returns for the view.

== SessionService

`SessionService` is the API an application and the advisors use; `DefaultSessionService` implements it on top of a `SessionRepository`.

[source,java]
----
SessionService sessionService = DefaultSessionService.builder()
    .sessionRepository(InMemorySessionRepository.builder().build())
    .defaultTimeToLive(Duration.ofDays(30))
    .build();

Session session = sessionService.create(CreateSessionRequest.builder()
    .metadata(SessionAttributes.PRINCIPAL_NAME, "alice")
    .build());

sessionService.appendMessage(session.id(), new UserMessage("Hello"));
sessionService.appendMessage(session.id(), new AssistantMessage("Hi, how can I help?"));

List<Message> prompt = sessionService.getActiveMessages(session.id());
List<SessionEvent> log = sessionService.getEvents(session.id(), EventFilter.all());
----

[cols="1,3"]
|===
| Method | Description

| `create(CreateSessionRequest)`
| Creates a session with the request's id (a random UUID by default), time to live and metadata; throws `SessionAlreadyExistsException` for a taken id.

| `findById(id)`, `findByIndex(name, value)`
| Looks a session up by id, or lists the sessions whose metadata holds a value under an indexed key, oldest first.

| `appendEvent(event)`, `appendMessage(id, message)`
| Appends an event to the session's log.
A `SystemMessage` is rejected unless `allowSystemMessages(true)` is set; see <<session-system-messages>>.

| `getEvents(id, filter)`, `getMessages(id)`, `getActiveMessages(id)`
| Reads the log through an `EventFilter`, or the messages of the whole log or of the active view.

| `compact(id, trigger, strategy)`
| Runs the trigger on the active view and, when it fires, the strategy; records the result as a boundary.
See <<session-compaction>>.

| `delete(id)`, `deleteExpiredSessions(before)`
| Deletes a session with its events, or every session that expired before the given instant.
|===

Appends are idempotent: an event id already stored for the session is a retried append and a no-op, so a replay after a failure writes nothing twice.
A compaction is an optimistic compare-and-swap on the session's event version: of two concurrent compactions only the first lands, and one that a new append overtakes is skipped and retried after the next turn.

[[session-event-filter]]
=== EventFilter

`EventFilter` selects what a read returns: the whole log or the active view, which event and message types, whether synthetic summary events are included, and a window.

[source,java]
----
EventFilter.all();                  // every event of the log, boundaries included
EventFilter.active();               // the message events of the active view
EventFilter.lastN(20);              // the newest 20 events, extended to the start of their turn

EventFilter.builder()
    .activeView(true)
    .messageTypes(Set.of(MessageType.USER, MessageType.ASSISTANT))
    .excludeSynthetic(true)
    .lastN(50)
    .build();
----

A `lastN` window keeps turns whole: when its oldest event is not a turn start, the window is extended back to the nearest user message before it, so a tool call is never read without its results.
The extension is skipped when no turn start precedes the window, or when a `messageTypes` filter hides the user messages.

`EventFilter.merge(other)` combines two filters: the other filter's types and window replace this filter's, and the two flags are OR-ed, so either side can opt in.
The memory advisor merges a per-request filter over its own this way.

[[session-compaction]]
== Compaction

As a conversation grows it exceeds the model's context window.
`SessionService.compact(id, trigger, strategy)` evaluates the `CompactionTrigger` on the active view and, only when it fires, runs the `CompactionStrategy`.
The result is one appended `COMPACTION` boundary followed by the summary events; when nothing should leave the view, nothing is written.

=== Triggers

[source,java]
----
new TurnCountTrigger(20);                              // more than 20 turns in the view
TokenCountTrigger.builder().threshold(4000).build();   // the view's estimated tokens reach 4000
CompositeCompactionTrigger.anyOf(new TurnCountTrigger(20), TokenCountTrigger.builder().threshold(4000).build());
----

`TurnCountTrigger` counts the non-synthetic user messages of the view.
`TokenCountTrigger` counts what is sent to the model, the latest stored system message, the summaries and the conversation, with a `TokenCountEstimator` (JTokkit by default), the same measure a token budget uses.

=== The window strategy

`WindowCompactionStrategy` keeps the recent conversation in the view and covers the rest.
Its `CompactionWindow` says how much stays: the last events, the last turns, or what fits a token budget.

[source,java]
----
WindowCompactionStrategy.builder().lastEvents(20).build();          // the default window
WindowCompactionStrategy.builder().lastTurns(10).build();
WindowCompactionStrategy.builder().tokenBudget(4000).build();
----

One pass, whatever the window:

. The latest stored system message is pinned at the front of the view and never summarized; every earlier stored system message is superseded and leaves the view with a pass that cuts.
. The events before the first turn, a pre-seeded preamble, are pinned too.
. Without a summarizer the summary a previous pass left is pinned and carried forward; with one it is fed to the summarizer and covered by the new summary.
. The window gives the raw cut among the turns.
The cut moves forward to the next turn start, so a turn is never split, and back to the newest turn when it would cover everything, so the newest turn stays even when it alone exceeds the window.
. The turns before the cut leave the view, the rest stay.

Pinned events use no slot of an event or turn window and come off a token budget first.
`CompactionResult` tells what the pass decided: the covered, pinned and preserved events, the summary and the estimated tokens saved.

=== Summarizing what leaves the view

A `CompactionSummarizer` condenses the covered turns into a summary turn that stands in for them: a user "shadow prompt" and an assistant summary, so the model keeps seeing a user/assistant alternation.
`ChatClientSummarizer`, in the advisor module, asks a `ChatClient` for a rolling summary: the prior summary is fed back as context, and the first preserved events are quoted for continuity.

[source,java]
----
CompactionStrategy strategy = WindowCompactionStrategy.builder()
    .lastTurns(10)
    .summarizer(ChatClientSummarizer.builder(summarizingChatClient)
        .overlapSize(2)
        .build())
    .build();
----

A summarizer that returns nothing declines, for example on a blank reply from the model: the view stays as it is and nothing is written, so a failed model call never loses history.
Any `CompactionSummarizer` works, a lambda included; `EventText.of(event)` renders an event the way the token estimates see it, tool calls and results included.

[[session-system-messages]]
=== System messages

A system message is configuration, not conversation: it comes from code, applies to every session at once and has no meaningful position in the history.
Supply the system prompt on every request, as `ChatClient` does with `defaultSystem` or `system(...)`, and keep per-session settings in the session's metadata.
`DefaultSessionService` therefore rejects a stored `SystemMessage` unless `allowSystemMessages(true)` is set (`spring.ai.session.allow-system-messages=true` with the auto-configuration).

When a session is created by one service and continued by another that does not know its setup, store the system prompt in the session instead.
The latest stored system message wins: it is the session's system prompt, compaction pins it first in the view, and the earlier ones are superseded.
To change it, store a new, complete one.

== ChatClient Advisors

Two advisors wire a session into a `ChatClient`.

* `SessionMemoryAdvisor` works on each model call.
It loads the active view into the prompt, prepending only what the prompt does not carry yet, and stores the request's user message or tool results and the model's reply.
* `SessionTurnAdvisor` works on each `ChatClient` call.
It creates the session on first use, stores the results of a tool loop that ended without a model round (a `returnDirect` tool, or a breached tool call limit) and compacts the session once the call has returned.

`SessionAdvisors` builds both at their default order around the tool-calling loop: the turn advisor outside it (`HIGHEST_PRECEDENCE + 200`) and the memory advisor inside it (`HIGHEST_PRECEDENCE + 1000`), once per round.

[source,java]
----
ChatClient chatClient = ChatClient.builder(chatModel)
    .defaultAdvisors(SessionAdvisors.builder(sessionService)
        .compaction(new TurnCountTrigger(20), WindowCompactionStrategy.builder().lastTurns(10).build())
        .asyncCompaction(true)                     // compact after the reply is returned
        .memory(memory -> memory.eventFilter(EventFilter.lastN(50)))
        .build())
    .build();
----

To place them yourself, build the advisors one by one with `SessionTurnAdvisor.builder(sessionService)` and `SessionMemoryAdvisor.builder(sessionService)`.
The memory advisor works on its own; the turn advisor is needed for compaction.

=== Context keys

[cols="2,3"]
|===
| Key | Purpose

| `SessionMemoryAdvisor.SESSION_ID_CONTEXT_KEY`
| The session a call runs on.
Equal to `ChatMemory.CONVERSATION_ID`, so `SessionAdvisors.session(id)` and `a.param(ChatMemory.CONVERSATION_ID, id)` are the same.

| `SessionMemoryAdvisor.SESSION_METADATA_CONTEXT_KEY`
| A `Map<String, Object>` of metadata for a session the advisor creates on first use, such as the agent attributes; ignored for an existing session.

| `SessionMemoryAdvisor.EVENT_FILTER_CONTEXT_KEY`
| A per-request `EventFilter` merged over the advisor's, to narrow the history of one call.

| `SessionMemoryAdvisor.REQUEST_EVENT_ID_CONTEXT_KEY`, `RESPONSE_EVENT_IDS_CONTEXT_KEY`
| Set by the advisor: the id of the event that stored the request's message, and the ids of the events that stored the reply's messages, to correlate a call with the log.
|===

=== What is stored

`MessageFilter` decides which messages are stored at all; `skipEmptyMessages()`, the default, skips assistant messages with no text, tool calls or media.
Tool calls and tool results are always stored, whatever the filter says: either half alone makes a prompt every provider rejects.
To keep tool traffic out of the prompt, hide it on read with a `messageTypes` filter instead; the advisor then drops a tool call left without its results from the prompt.

[source,java]
----
SessionMemoryAdvisor.builder(sessionService)
    .messageFilter(MessageFilter.containsText("confidential").negate().and(MessageFilter.skipEmptyMessages()))
    .eventFilter(EventFilter.builder().messageTypes(Set.of(MessageType.USER, MessageType.ASSISTANT)).build())
    .build();
----

Both advisors run their session writes on a `Scheduler` (`BaseAdvisor.DEFAULT_SCHEDULER` by default), also for a streamed call, so nothing blocks the model's thread.

== JDBC Repository

`JdbcSessionRepository` stores sessions in three tables: `AI_SESSION` (id, expiry, metadata JSON, event version), `AI_SESSION_INDEX` (the indexed metadata attributes) and `AI_SESSION_EVENT` (the log, ordered by a database-assigned `seq`).
PostgreSQL, MySQL, MariaDB and H2 are supported; the dialect is detected from the database metadata, and another database takes a `JdbcSessionRepositoryDialect` of your own.

The schema scripts are on the classpath under `org/springframework/ai/session/jdbc/schema-<platform>.sql`.
The auto-configuration applies them per `initialize-schema`; otherwise apply them with Spring Boot's SQL initialization or your migration tool.

[source,java]
----
@Bean
SessionRepository sessionRepository(DataSource dataSource) {
    return JdbcSessionRepository.builder()
        .dataSource(dataSource)                       // the dialect is detected
        .indexedAttributes(Set.of("tenant"))          // besides the principal name
        .build();
}
----

An event is stored in four columns: the event type, the message type, the message text (its own column, so a store can search it) and a JSON payload holding the message's parts and metadata, so media, tool calls, tool results and provider-signed reasoning survive a round trip.

== Auto-configuration

The starter registers two auto-configurations.
`SessionServiceAutoConfiguration` creates a `SessionService` on top of the single `SessionRepository` bean; `JdbcSessionRepositoryAutoConfiguration` creates the `JdbcSessionRepository` on top of the single `DataSource`.
Declare your own bean of either type and the auto-configuration backs off.
A `SessionServiceDecorator` bean wraps the auto-configured service, for a cross-cutting concern such as authorization.

[cols="2,1,3"]
|===
| Property | Default | Description

| `spring.ai.session.time-to-live`
| `60d`
| The time to live of a session the service creates without one of its own.

| `spring.ai.session.allow-system-messages`
| `false`
| Whether a `SystemMessage` may be stored in a session.

| `spring.ai.session.repository.jdbc.initialize-schema`
| `embedded`
| When the schema script runs: `embedded`, `always` or `never`.

| `spring.ai.session.repository.jdbc.schema`
| `classpath:org/springframework/ai/session/jdbc/schema-@@platform@@.sql`
| The schema script; `@@platform@@` resolves to the detected database.

| `spring.ai.session.repository.jdbc.indexed-attributes`
| empty
| The metadata keys indexed besides the principal name, so `findByIndex` answers for them.
|===

== Implementing a Repository

A store implements `SessionRepository`: the session lookups, the idempotent `appendEvent`, the version-checked `appendEvents` a compaction uses, and `findEvents(sessionId, filter)`.
`EventFilter.apply(events)` and `CompactionBoundary.project(log)` are the reference implementations of the filter and of the view, for a store that reads the whole log and filters in memory; the JDBC repository pushes the same rules down to SQL.

The `spring-ai-session` test-jar ships `AbstractSessionRepositoryContractTests`: extend it, return your repository from `createRepository()`, and the contract the in-memory and JDBC repositories pass runs against yours.
